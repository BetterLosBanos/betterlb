# BetterLB Architecture Documentation

> **Note:** Generated by Maestro | Last updated: 2026-02-27T12:00:00.000Z

## Overview

**BetterLB** is a municipal government portal for Los Baños, Laguna, Philippines - a fork and localization of BetterGov.ph. It provides transparent access to government services, legislative documents, elected officials, departments, and municipal data.

**Architecture Type:** JAMstack (Static Frontend + Serverless Backend)
**Deployment:** Cloudflare Pages (Frontend) + Cloudflare Pages Functions (API)
**Database:** Cloudflare D1 (SQLite-based, edge-native)
**Search:** Meilisearch (self-hosted)
**Languages:** TypeScript (Frontend), Python (Data Pipeline), SQL (Database)

### Authentication

**Admin Authentication Flow:**
1. User clicks "Admin Login"
2. Redirect to Google OAuth (`/api/admin/auth-google/login`)
3. Google redirects to callback (`/api/admin/auth-google/callback`)
4. Verify against `AUTHORIZED_USERS` env var
5. Set encrypted session cookie
6. Redirect to `/admin`

**Protected Route Middleware:**
```typescript
export function protectedRoute(handler: Handler) {
  return async (request: ApiRequest) => {
    const session = await getSession(request);
    if (!session) {
      return new Response('Unauthorized', { status: 401 });
    }
    return handler(request);
  };
}
```

## Database Architecture (Cloudflare D1)

### Database Technology

**Cloudflare D1:**
- SQLite-based relational database
- Edge-optimized (replicated globally)
- Serverless scaling (pay per query)
- Schema migrations via `wrangler d1 migrations`

### Connection Details

**Local Development:**
```bash

```

**Remote Database:**
- Name: `betterlb_openlgu`
- Binding: `BETTERLB_DB` (variable name in code)
- ID: `67f71e98-fece-4460-b3b6-40f6f8742d89`

### Schema Overview

**Core Tables:**

```sql
-- Terms (elected terms)
terms (id, term_number, ordinal, name, start_date, end_date, year_range, mayor_id, vice_mayor_id)

-- Persons (councilors, mayors, officials)
persons (id, first_name, middle_name, last_name, suffix, aliases)

-- Memberships (person-term relationships)
memberships (id, person_id, term_id, chamber, role, rank)

-- Legislative Sessions
sessions (id, term_id, date, number, type, location)

-- Session Attendance (absent-only model)
session_absences (session_id, person_id)

-- Legislative Documents
documents (id, document_number, type, title, date, pdf_url, session_id, status)

-- Document Authors (many-to-many)
document_authors (document_id, person_id)

-- Committees
committees (id, name, type, description)

-- Committee Memberships
committee_memberships (id, person_id, committee_id, term_id, role)

-- Review Queue (human verification)
review_queue (id, item_type, item_id, reason, status)

-- Data Conflicts (source reconciliation)
data_conflicts (id, entity_type, entity_id, field, source_value, resolved_value)
```

**Views:**
```sql
-- Author Productivity
v_author_productivity (documents authored per person)

-- Session Attendance Summary
v_session_attendance (attendance rates per session)
```

### Database Relationships

```
terms ───┬─── memberships ──── persons
         │
         ├─── sessions
         │     │
         │     ├─── session_absences ──── persons
         │     │
         │     └─── documents
         │            │
         │            └─── document_authors ──── persons
         │
         └─── committees
                │
                └─── committee_memberships ──── persons
```

### Data Model Patterns

**Absent-Only Attendance Model:**
- Only record absences (not present)
- Calculate attendance rate: `1 - (absences / total_members)`

**Document Status Workflow:**
```
pending → approved → published
    ↓
  rejected
```

**Human-in-the-Loop Verification:**
- Pipeline inserts `pending` documents into `review_queue`
- Admin reviews and marks as `approved` or `rejected`
- Only `approved` documents appear in public API

## Data Pipeline Architecture

### Pipeline Overview

The data pipeline transforms raw legislative PDFs into structured JSON data.

**Technology:**
- Python 3.x
- PDF extraction: `pdfplumber`, `PyPDF2`, `pdf2image`
- Validation: `jsonschema`, `aiohttp`

### Pipeline Stages

```
┌─────────────────┐    ┌─────────────────┐    ┌─────────────────┐
│   1_scrape.py   │───▶│ 1.5_normalize   │───▶│   2_download.py  │
│  (Web Scraping) │    │   (Normalization)│   │  (PDF Download) │
└─────────────────┘    └─────────────────┘    └─────────────────┘
                                                        │
                                                        ▼
┌─────────────────┐    ┌─────────────────┐    ┌─────────────────┐
│   4_generate.py  │◀───│   3_parse.py    │◀───│  PDF Files       │
│ (JSON Output)   │    │  (PDF Parsing)  │    │  (Local Storage) │
└─────────────────┘    └─────────────────┘    └─────────────────┘
```

### Stage Details

**1. `1_scrape.py` - Web Scraping**
- Scrapes official Los Baños legislative portal
- Discovers available documents
- Extracts metadata (numbers, dates, titles)

**1.5. `1.5_normalize.py` - Data Normalization**
- Standardizes date formats (ISO 8601)
- Normalizes document numbering
- Removes extra whitespace

**2. `2_download.py` - File Download**
- Downloads PDFs to `pipeline/data/pdfs/`
- Retries failed downloads
- Skips already downloaded files

**3. `3_parse.py` - PDF Parsing**
- Extracts text from PDFs
- Handles OCR for scanned documents
- Identifies document metadata

**4. `4_generate.py` - JSON Generation**
- Converts parsed data to JSON schema
- Generates structured output
- Outputs to `src/data/legislation/`

### Citizens Charter Extraction

**Purpose:** Extract service requirements and steps from Citizens Charter PDFs

**Tools:**
- `citizens_charter_extractor.py` - Main orchestrator
- `cc_data_validator.py` - JSON schema validation
- `cc_merge_utils.py` - Merge utilities with backup
- `vision_prompt_templates.py` - Prompt templates for AI extraction

**Output Location:**
`src/data/citizens-charter/citizens-charter.json`


## Caching Strategy

### Cache Layers

**1. Cloudflare CDN (Static Assets)**
- Caches built frontend files (`dist/`)
- TTL: 1 year (with content hash)

**2. Cloudflare KV (Weather Data)**
- Caches PAGASA weather API responses
- TTL: 15 minutes

**3. Browser Cache (API Responses)**
- Standard HTTP caching headers
- Cache-Control: `public, max-age=300` (5 minutes)

**4. Meilisearch (Search Results)**
- In-memory search index
- Updated via pipeline runs

### Cache Invalidation

**Manual:**
- Deployments clear CDN cache automatically
- KV entries expire via TTL

**Automatic:**
- Content hash in bundle filenames
- ETags for API responses

## Architecture Decision Records

### ADR-001: JAMstack over Monolith
**Decision:** Use JAMstack (Cloudflare Pages + Functions) instead of traditional monolithic server.

**Rationale:**
- Edge deployment (low latency globally)
- Serverless scaling (pay-per-use)
- Simplified operations (no server management)
- Built-in DDoS protection

**Trade-offs:**
- Limited runtime (Edge vs Node.js full API)
- Cold starts on first request
- Database connection limits (D1)

### ADR-002: D1 over PostgreSQL
**Decision:** Use Cloudflare D1 (SQLite) instead of PostgreSQL.

**Rationale:**
- Edge-native (replicated globally)
- Single database for local and remote
- Seamless integration with Pages Functions
- Lower cost at low traffic

**Trade-offs:**
- Less feature-rich than PostgreSQL
- Limited connection pooling
- Single-region writes

### ADR-003: Kapwa Fork over Upstream
**Decision:** Fork Kapwa Design System instead of using upstream bettergovph/kapwa.

**Rationale:**
- Municipal branding requirements
- Custom color scheme
- Local component needs

**Trade-offs:**
- Maintenance burden (merge upstream changes)
- Divergence over time

### ADR-004: Absent-Only Attendance
**Decision:** Record only absences, not presence, for legislative sessions.

**Rationale:**
- Simpler data entry (fewer records)
- Assumes present unless marked absent
- Reduces manual entry workload

**Trade-offs:**
- Cannot distinguish "present but not voting"
- Requires total member count for calculation

### ADR-005: Static JSON over CMS
**Decision:** Store directory data (departments, barangays) as JSON files instead of CMS.

**Rationale:**
- Version control (Git history)
- No database queries for static data
- Faster page loads
- Easier content reviews

**Trade-offs:**
- Requires rebuild for content changes
- No non-technical editor access
- Larger bundle size
